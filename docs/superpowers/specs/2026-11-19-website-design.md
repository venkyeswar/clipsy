# Clipsy website — design

## Intent and why
Clipsy (Linux clipboard history manager, Rust + GTK4) needs a public website that (1) lets a visitor understand what it is within seconds and (2) lets them download/install it. Users have also hit `sudo` problems, so install help is a first-class job. No login, no backend. When a new release (.deb etc.) is published, the site must reflect it automatically with no manual step.

## Goals
- Landing page that explains Clipsy AND offers the download in the first screen.
- Always-current downloads: latest release prominent, previous releases listed, with checksums.
- Install guidance per method (Snap / Ubuntu App Center link, .deb, no-sudo install, build from source) with copy buttons.
- Help section answering the real support questions (Super+V conflict, Wayland/GNOME extension, no sudo, uninstall).
- Polished animation, proper dark and light themes (system default + toggle), friendly and fast.

## Non-goals
- No accounts, comments, analytics dashboards, blog CMS, or server code. No i18n in v1.

## Anti-goals
- A generic "SaaS template" look (identical rounded cards, gradient washes, fade-up-on-everything).
- A stale site that lists old versions as latest; a download button that 404s.
- Motion that ignores `prefers-reduced-motion`; poor contrast in either theme.

## Constraints (from the user)
- React app. UI components come only from shadcn/ui (plus Tailwind for styling). Animation via the Motion library and CSS (animation is not a UI component).
- Proper dark and light palettes with accessible contrast (WCAG AA body text).
- Frontend-design skill guidance applies: deliberate palette/type, one memorable moment, restraint.

## Approaches considered
1. (Chosen) Static Vite + React + TypeScript site in `website/` of this repo; at runtime fetch `https://api.github.com/repos/venkyeswar/clipsy/releases` in the browser; deploy to GitHub Pages via a GitHub Actions workflow. Auto-updates with zero rebuilds; no hosting cost; one repo.
2. Rebuild-and-redeploy the site from the release workflow with the release list baked in. Rejected as the primary mechanism: needs a pipeline hop and goes stale if the hop fails. Kept only as the fallback snapshot (see below).
3. Next.js/SSR on a server host. Rejected: a server and cost for a site that is static content plus one public API call.

## Decisions (my calls — user delegated; user can override)
- Location: `website/` in the clipsy repo; separate `deploy-website.yml` workflow (build on push to main touching `website/**`, deploy to GitHub Pages).
- Stack: Vite, React 18, TypeScript, Tailwind, shadcn/ui, Motion, react-router NOT needed (single page with anchored sections; hash links).
- Releases: client-side fetch of the GitHub Releases API with `sessionStorage` cache (10 min) and a build-time fallback snapshot `website/src/data/releases.snapshot.json` (generated by a script during build) used when the API fails or is rate-limited (unauthenticated limit is 60 requests/hour/IP). Show a Skeleton while loading. Never show an error wall: fall back to the snapshot and a link to the GitHub releases page.
- Asset detection: pick `*.deb`, the no-sudo tarball (`*.tar.gz`), and `SHA256SUMS` from each release's assets by filename pattern; a release missing a .deb still renders without a broken button.
- Prerequisite (separate change, done first): a release workflow that on a `v*` tag builds the .deb (packaging/build-deb.sh), a no-sudo tarball with `install.sh`, and `SHA256SUMS`, and attaches them to a GitHub Release. The site depends on this; today no workflow produces a Release.
- App Center / store link: Ubuntu App Center deep link `snap://clipsy` plus a Snapcraft Store page link; shown only once the snap is published to the store (config flag in `website/src/config.ts`).

## Calls made after the builder check (my calls — user can override)

1. **Release workflow is a separate plan, done first.** Plan A = the release workflow + no-sudo install (the `v*`-tag workflow building the .deb from packaging/build-deb.sh, the tarball, and SHA256SUMS; the app writing its own menu entry to `~/.local/share/applications` on first run). Plan B = this website. Plan B does not start until Plan A has produced the first release.
2. **No-sudo tarball contract (what the site may promise).** Filename `clipsy-<version>-linux-x86_64.tar.gz` containing the `clipsy` binary, the desktop file, the icon, the GNOME extension, `install.sh` and `uninstall.sh`. `install.sh` installs only under `~/.local` (bin, share/applications, share/icons, GNOME extension) and never calls sudo; it requires GTK4 and libadwaita to already be installed (default on Ubuntu 24.04 GNOME) and says so if they are missing. The app already manages its shortcut/autostart and installs the GNOME extension per user, so Super+V and the Wayland extension work without sudo; the site states only what has been verified. Data stays in `~/.local/share/clipsy`; `uninstall.sh` removes the install and offers to keep or delete that data.
3. **Snap / App Center.** `config.ts` has `snap: { channel: "stable" | "edge" | null }`. `null` hides the App Center/Snap tab; `edge` shows `sudo snap install clipsy --edge`; `stable` shows `sudo snap install clipsy`. App Center deep link `snap://clipsy` only when not null.
4. **Zero-release state.** The site is not deployed until the first release exists. If the API and snapshot are ever both empty, the hero CTA becomes "View on GitHub" and Downloads shows a link to the releases page.
5. **Snapshot freshness.** The deploy workflow also triggers on `release: published` (and `workflow_dispatch`) so the build-time fallback snapshot is regenerated on every release, in addition to pushes touching `website/**`.
6. **Architectures and pre-releases.** v1 ships amd64 only; assets are matched by filename pattern and an arch is parsed from the name so more can be added later. Drafts and pre-releases are never "latest"; pre-releases appear in Previous versions with a "Pre-release" Badge. Version sorting uses semver, not publish date.

## Visual direction (proposal — review against defaults done)
- Subject world: a clipboard that remembers. Signature motifs: the real popup UI (search, tabs All/Text/Images/Files/★, trash button) and keycaps (the app already draws shortcut keycaps).
- Palette (tokens as CSS variables per shadcn convention; builder samples the exact accent from the app's own CSS/screenshot, the app uses an orange accent on dark):
  - Dark: background Slate Night `#171a21`, surface `#20242d`, text `#e9ebf1`, muted `#9aa1b0`, accent Ember `#f0592b`, link/secondary Lagoon `#3fb8c9`.
  - Light: background Cool Paper `#f5f7fb` (not cream), surface `#ffffff`, text `#1b1f29`, muted `#5d6577`, accent Ember `#d8431a`, secondary Lagoon `#0f8aa0`.
  - Verify AA contrast for every text/background pair in both themes; adjust values if any pair fails.
- Type: display Familjen Grotesk (headlines, tight tracking), body Onest, commands/keycaps JetBrains Mono. Scale ~1.25; line length under 70 characters; sentence case everywhere; no all-caps eyebrow labels; no single-word accent in headlines.
- Layout: left-aligned text. Hero is two columns on desktop (copy + CTAs left, live popup demo right), stacked on mobile with the demo below the CTAs. Sections below use varied structure (not identical cards): a wide install tabs panel, a downloads table, a features list with the demo reused, a shortcuts keycap sheet, an FAQ accordion.
- Hero copy (plain language, builder may polish): headline "Everything you copied, one shortcut away." Subhead: "Clipsy keeps your clipboard history on your computer. Press the shortcut, search, and paste anything you copied earlier." Primary CTA: "Download .deb v{latest}" (from the live release); secondary: "Other ways to install" (scrolls to Install). Under the CTAs, a small link: "Can't use sudo? Install to your home folder."
- The one memorable moment: the hero demo — a faithful, working mini popup built from shadcn parts (Input, Tabs, Button, Badge). On load it auto-plays a short sequence (three copies arrive and stack, the search narrows, a pinned item gets starred), then becomes fully interactive (type to search, switch tabs, press the trash to see the confirm dialog with "Also remove pinned items"). With `prefers-reduced-motion` it shows the final state with no autoplay.
- Other motion: only in response to action (tab change, copy-button "Copied" confirmation via Sonner toast, theme toggle). No scroll-triggered fade-ins on every section.
- shadcn components to use: Button, Tabs, Table, Accordion, Badge, Input, Dialog/AlertDialog (demo confirm), Sonner, DropdownMenu (version picker), Skeleton, Tooltip, Sheet (mobile nav), Separator, Switch/Toggle (theme). Keycaps are a small custom component composed with Tailwind (not a UI-library component).

## Page structure (single page, anchored sections)
1. Header: logo, links (Install, Downloads, Help, GitHub), theme toggle.
2. Hero (above).
3. How it works (copy anything → summon with the shortcut → pick and paste): prose with the demo, not numbered cards.
4. Install: Tabs — Ubuntu App Center / Snap, .deb, Without sudo, From source — each with copy-able commands and a one-line note on what it does.
5. Downloads: latest release highlighted (version, date, .deb + tarball + checksum), "Previous versions" table with a version DropdownMenu/rows, link to full release notes on GitHub.
6. Features (list): clipboard history for text/images/files, search, pin, clear per tab, private by default (password-manager copies skipped, stays on the computer), works on X11 and GNOME Wayland.
7. Shortcuts: keycap cheat sheet (↵ paste, ⇧↵ plain, ⌫ remove, plus the global shortcut).
8. Help: Accordion — "Super+V does nothing", "Does it work on Wayland?", "I can't use sudo", "How do I uninstall?", "Where is my data stored?".
9. Footer: GitHub, license (GPL-3.0), report an issue.

## Quality floor
Responsive to 360px width, visible keyboard focus, semantic landmarks, `prefers-reduced-motion` respected, dark/light verified, Lighthouse accessibility >= 95, no layout shift while releases load (Skeleton with fixed height), all external links `rel="noopener"`.

## Left to the builder
Exact accent sampling from the app, final copy polish, demo timing, repo scaffolding details, favicon/logo from the existing app icon, snapshot-generation script, Pages base-path config, test setup (Vitest for the release-parsing logic: asset detection, version sorting, fallback).
